# #4267 shadow-tree probe — the reported failure does not reproduce

Wave-1 probe for epic zudolab/zudo-doc#4271, sub-issue #4272. Diagnosis only; no
production code was changed.

**Headline:** on `@takazudo/zfb@2.18.0` + a packed `@takazudo/zudo-doc@5.25.0`
tarball, **eleven consumer topologies — ten fully green, one green through the
bundler — including the reporter's exact install shape (a real `pnpm install`
workspace sub-package whose `node_modules/@takazudo/zudo-doc` is a symlink into
the workspace-root `.pnpm`).** All three hypotheses the epic listed are refuted as sufficient
causes. The epic's inferred mechanism (zfb generates a relative
`../node_modules/...` shim specifier) is **confirmed as fact**; the claim that
this specifier fails to resolve for pnpm-symlinked consumers is **not**
reproducible here.

---

## 1. Established: the shim, verbatim

zfb 2.18.0 materialises every injected route as a generated `.tsx` overlay in a
temp dir `/tmp/zfb-pkg-routes-<rand>/pages/`, then symlinks those files into the
bundler shadow root `/tmp/zfb-bundler-<rand>/`. Captured bytes (static route):

```tsx
// AUTO-GENERATED by zfb (package-owned routes, #1193). Do not edit.
// Re-exports the package entrypoint's default page component;
// the build renders this overlay module like any pages/ file.
export { default } from "../node_modules/@takazudo/zudo-doc/routes-src/404.tsx";
```

Dynamic route (`pages/docs/[[...slug]].tsx`), one directory deeper, hence `../../`:

```tsx
// AUTO-GENERATED by zfb (package-owned routes, #1194). Do not edit.
// Dynamic package route: re-exports the entrypoint's default page
// component and surfaces a TOP-LEVEL `paths` the extractor can see.
export { default } from "../../node_modules/@takazudo/zudo-doc/routes-src/docs-slug.tsx";
// Runtime paths() wrapper: imports the package's real `paths` and re-declares
// it top-level so the extractor defers to the V8 `__paths__` worker (#1194).
import { paths as __zfb_pkg_paths } from "../../node_modules/@takazudo/zudo-doc/routes-src/docs-slug.tsx";
export async function paths() { return await __zfb_pkg_paths(); }
```

These are byte-for-byte the specifiers in the #4267 report. **zudo-doc never emits
a relative string** — `packages/zudo-doc/src/plugins/routes.ts` hands
`ctx.injectRoute` an absolute path; zfb relativises it against the shim's
position. The epic's inference on this point is now fact, not inference.

Observed but **not** explained: the emitted specifier is the clean
`.../node_modules/@takazudo/zudo-doc/routes-src/...` even when
`node_modules/@takazudo/zudo-doc` is a pnpm symlink — never a `.pnpm/` realpath.
That is surprising, because the absolute path zudo-doc hands `injectRoute` is
derived from `require.resolve()` (`plugins/routes.ts`), which resolves symlinks,
so under pnpm it *is* a `.pnpm/...` realpath. zfb must therefore re-lexicalise
the path (or relativise it against something other than the value it was given)
before writing the shim; that step was not located in the 2.18.0 binary. Treat
the clean specifier as a captured observation, not as a mechanism this probe
understands — a consumer whose realpath layout defeats the re-lexicalisation
would be exactly the missing ingredient §7 asks the reporter for.

## 2. Established: why it resolves — the shadow root symlinks `node_modules`

In the ordinary single-root case the bundler shadow root contains:

```
/tmp/zfb-bundler-clXCP4/
  entry.mjs  tsconfig.json  pages/  src/  content/  .zfb/
  node_modules -> /<projectRoot>/node_modules        # absolute symlink
```

So `../node_modules/@takazudo/zudo-doc/routes-src/404.tsx` from
`<shadow>/pages/404.tsx` lands on the real project `node_modules`, traverses the
pnpm symlink through the OS, and resolves. In every run observed here the
`routes-src/` tree was reached in place — it was never copied into an
exact-node-modules isolation root.

`--preserve-symlinks` was **not** passed for the SSR/page bundle in any
single-root run. zfb's own docblock (extracted from the 2.18.0 binary) states it
is passed *"whenever a custom `node_modules_dir` is configured"*. That branch was
observed only when the project root has no `node_modules` of its own (pnpm
`node-linker=hoisted`), where the shadow root re-roots one level up
(`<shadow>/apps/site/...` with `node_modules` at `<shadow>/`). That build's SSR
bundle still resolved every shim.

`bundler: skip injected-route entrypoint (not a first-party file under the
project root)` **never fired** — not in any of the eleven builds. Every run logged
`info package route '/404' -> pages/404.tsx` and friends, i.e. all five routes were
injected.

## 3. Correction to the issue's probe recipe

`ZFB_KEEP_SHADOW_SESSION=1 zfb build` does **nothing**. In 2.18.0 that variable
gates only the *dev* persistent shadow session (`zfb-shadow-session-*` under
`XDG_CACHE_HOME`); `zfb build` allocates and unconditionally tears down its own
tempdirs (`zfb-bundler-*`, `zfb-pkg-routes-*`, `zfb-exact-node-modules-*`). No
keep flag exists for the build path — the full `ZFB_*` inventory in the binary
confirms it.

Two working substitutes were used instead, and both are cheap enough for the
wave-3 gate:

- `TMPDIR=<dir> zfb build` with a tight `cp -a` poll loop over `<dir>/zfb-*`.
- `ZFB_ESBUILD_BIN=<wrapper>` — a shell wrapper that records `argv` and `cp -a`s
  the `zfb-bundler-*` root before exec'ing a real esbuild. Note the binary pins
  esbuild `0.25.12`; a different version fails the *islands* pass, but the SSR
  argv and the shadow snapshot are captured before that.

## 5. Reproduction recipe (for the wave-3 gate)

This recipe is exact and runnable; it currently produces a **passing** build, so
wave 3 must treat it as the shape to extend, not as a red test.

```bash
# 1. pack the package under test
cd packages/zudo-doc && npm pack --pack-destination /tmp/probe

# 2. lay out a pnpm workspace with the consumer as a sub-package
mkdir -p /tmp/repro/apps/site && cd /tmp/repro
printf 'packages:\n  - "apps/*"\n' > pnpm-workspace.yaml
echo '{ "name": "repro-ws", "private": true, "version": "0.0.0" }' > package.json

# 3. fixture body: packageOwnedRoutes on, pages/ holds ONLY a non-shadowing index
cp -r <repo>/packages/zudo-doc/src/__tests__/fixtures/route-injection-i18n/. apps/site/
mkdir -p apps/site/pages apps/site/.zfb && echo '{}' > apps/site/.zfb/doc-history-meta.json
# write apps/site/pages/index.tsx (any trivial page)

# 4. apps/site/package.json depends on the TARBALL, so pnpm plants a symlink
#    into the workspace-root .pnpm store (never a real extracted dir)
#    deps: @takazudo/zfb@2.18.0, @takazudo/zfb-md-wasm, @takazudo/zfb-runtime,
#          @takazudo/zudo-doc: "file:/tmp/probe/takazudo-zudo-doc-<v>.tgz",
#          preact, preact-render-to-string, zod
pnpm install --ignore-scripts

# 5. build
cd apps/site && ./node_modules/.bin/zfb build
```

Verify the install shape before believing a green result:

```bash
readlink apps/site/node_modules/@takazudo/zudo-doc
# ../../../../node_modules/.pnpm/@takazudo+zudo-doc@.../node_modules/@takazudo/zudo-doc
```

To inspect the shims, prefix step 5 with `TMPDIR=/tmp/probe/tmpd` and poll
`/tmp/probe/tmpd/zfb-pkg-routes-*/pages/` during the (≈1.2s) build.

## 6. Hypotheses — verdicts

| | Hypothesis | Verdict |
|---|---|---|
| 1 | real dir vs pnpm symlink (the epic's leading hypothesis) | **Refuted.** Rows 2, 3, 8, 9 are all genuine pnpm symlinks and all green. The realpath escaping the project root (rows 3, 9) changes nothing, because the emitted specifier came out lexical in every run (§1 — observed, not explained) and the shadow root symlinks the whole project `node_modules`. |
| 2 | workspace sub-package resolving upward to a workspace-root store | **Refuted.** Row 9 is exactly that, built by real pnpm, and green. |

## 7. The call: neither, on this evidence

**This is not established as a zudo-doc-side bug, and not established as a zfb
2.18.0 regression.** The evidence is positive, not merely absent: the exact
combination reported broken (zfb 2.18.0 + zudo-doc 5.25.0, packageOwnedRoutes on,
all three routes injected, pnpm symlink, workspace sub-package) builds green ten
different ways on this machine (plus an eleventh whose page bundle resolved
before failing for an unrelated reason), and the resolution mechanism that would
have to fail is directly observable working.

What *is* established, and is useful to wave 2 regardless:

- The relative-shim mechanism is real and is zfb's, not zudo-doc's. Any fix that
  removes zudo-doc's dependence on the shim's position — the epic's "bare
  `exports` subpath" option — would be robust against it.
- `.zudo-doc/routes-src` staging (#4224) is **not** needed for resolution in any
  topology tested. Its removal is not falsified by anything measured here.

**Consequence for the epic: wave 2 cannot choose a fix from this evidence.** The
missing ingredient lives in the reporter's private project. The cheapest way
forward is to collect it from there rather than guess:

1. Re-run the failing build with `TMPDIR=<dir>` and the poll loop from §3, and
   attach the `zfb-pkg-routes-*/pages/*.tsx` shims plus a listing of the
   `zfb-bundler-*` root (specifically: is `node_modules` there, and is it a
   symlink?).
2. Capture the full SSR esbuild `argv` via the `ZFB_ESBUILD_BIN` wrapper — in
   particular whether `--preserve-symlinks` is present, which per §2 means zfb
   took the custom-`node_modules_dir` branch.
3. Report their `.npmrc` (`node-linker`, `hoist` settings), the consumer's
   `zfb.config.ts` (`adapter`, `bundle.exclude`, `docsDir`), and whether the
   project root has its own `node_modules`.

Item 2 is the highest-value single datum: every green run above took the
non-`--preserve-symlinks` branch for the page bundle, and the one run that did
take the `--preserve-symlinks` branch (row 11) also re-rooted the shadow tree —
which is the only observed configuration where shim depth and `node_modules`
depth could plausibly disagree.
