The baseline came from a clean worktree of main `6b7ba8e4b6aee83909c7dbf1e873d21fe84ebb84` (zfb 4.5.4), where all 20 assertions passed and reproduced the #4606 hashes. The candidate came from head `957c252d`, where the three strict fingerprints failed with the same received hashes CI reported.

`python3 scripts/a2-causal-diff.py` compared the two captures with reference source `6b7ba8e4b6aee83909c7dbf1e873d21fe84ebb84`. It reported `DIFFERENCES_REQUIRE_REVIEW` / `OBSERVED_ONLY_UNVERIFIED_FRESHNESS`, with `residualEqual: true` and an empty residual diff on all three pages, and no changed stylesheets.

- **Lengths.** In 404, getting-started and coverage order, raw lengths are 57,025, 67,457 and 78,909. They are the same before and after the bump.
- **Build identity.** The pages contain 1, 2 and 4 `data-zfb-build` values respectively, and every one changes from `51627089654423fd` to `d5db75b78169675d`. The hashed islands bundle name moves with it.
- **Residual.** Replacing only those candidate values with the baseline value reproduces all three accepted normalized captures exactly, with no other byte differences.
- **New strict hashes,** in page order: `233b2efe429e788ed2a3f88dfe7161aa88cff786fd43ce202ae03cf59fbc02d8`, `3bde945f9df29ee208c9e97f17649e335218085b2c4b9f3dc8568432fb263096` and `6cedf6d35833a623b3fc83243ad7d63561c82cd3eceb2ff769666057bc84a89c`.

The identity is native ZFB build metadata derived from esbuild's resolved browser graph (since 4.5.4). The 4.6.0 family bump is inside that graph, which is why the identity moved even though `zfb-runtime` reports no package-specific changes.

`compiled.css` did not change. This update keeps the native identity in the fingerprint, the normalizer and every A2 assertion. Fresh final-head CI must still run and pass the strict A2 subset; this forensic comparison alone is not acceptance.
