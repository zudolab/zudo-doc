## Sidebar input baseline control

The exploratory DOM-token probe compared the reconstructed pinned baseline
`337b9f110793dccb4759bddd5273eab38cd9d2f0` (`@takazudo/zfb` 2.22.1) with the
v4.2.1 smoke preview. The v4 capture ran with checkout HEAD
`c374657e0eeee8a157a6d41f8b5dff937cefacdc`; its product source matches
`2926b1da1ee1b1f3d402fbe02543a1d87ba0d9fc`, with the #4468 fixture article as
the only difference in the checked product/fixture paths. The control uses
the existing `/docs/guides/page-1/` → `/docs/guides/code-blocks-test` route pair.
Inside each build, `currentSlug` was the only changed top-level SidebarTree
prop, and ThemeToggle props were equal.

Both the first capture and the hydration-gated repeat recorded one document
request before and after navigation, unchanged `performance.timeOrigin`, a
preserved aside/SidebarTree root, and one fulfilled view transition. Both
replaced the filter input and returned its value to empty; both updated
`aria-current` to `page`. The hydration-gated repeat waited for ThemeToggle's
public pending attributes to clear before writing tokens and confirms the
input reset in both versions. It also observed that the ThemeToggle button
identity differed (replaced in v2, retained in v4); this is recorded as an
observation, not adopted as a parity contract.

The initial diagnostic used speculative identity-retention assertions and
therefore exited 1 in the v2 project; the v4 project passed. Its report was
written before assertions. The hydrated rerun produced the same comparison.
The new permanent test now asserts the measured filter reset, then exercises
filtering again and verifies the active route; it does not add a persistence
repair or an assertion about ThemeToggle button identity.

Compact reports and the diagnostic probe are in
[`runtime-controls/`](../../../_temp-resource/4430-zfb3-migration/parity/4.2.1/runtime-controls/).
The JSON preserves both captures, including the initial run's unmeasured
hydration state and the hydrated rerun's cleared pending markers.

## Injected-dev CSS harness correction

The first mobile browser attempt failed because the disposable no-stub project
had no `src/styles/global.css`; its generated utility classes referenced
undefined spacing/icon tokens and the mobile button measured 0×0. The probe
now copies the exact generated template entrypoint
`packages/create-zudo-doc/templates/base/src/styles/global.css` into the temp
project. This fixture has `designTokenPanel: false`, so the template correctly
does not import zdtp. It also needs no explicit zudo-wind source import because
the configured preset owns reset and utility generation.

The guarded command was:

```sh
bash "$HOME/.codex/scripts/heavy-guard.sh" -- /tmp/zudo421-request-runtime-probe/run.sh
```

With the consumer CSS contract, the browser test passed in 4.9s and the heavy
guard reported PASS in 6s. The mobile button measured 40×52px; desktop filter
hydration, desktop SPA navigation, mobile drawer open, and mobile SPA navigation
all passed, with no extra document request. The before/after logs are preserved
under `runtime-controls/`; the initial CSS-less failure remains in the
`dev-css-before-contract.log` file.

changes currentSlug and resets input in both exact controls. Neither proves
mutated local signal continuity beneath an unchanged nested island during real
same-document navigation. A dedicated authored consumer is prepared in
[`runtime-controls/persistence-browser/`](../../../_temp-resource/4430-zfb3-migration/parity/4.2.1/runtime-controls/persistence-browser/).

references, and unchanged Document/timeOrigin/document request counts cover
unchanged repeated navigation, changed props, host preservation, and structural
replacement. Private mount-handle identity is not inspected; observable scope
continuity is the claim. Project/spec typechecks and script syntax pass.
Manager browser execution and result capture remain pending; no parity sign-off
is added by preparing this control.
