Design notes & open questions

  • Naming. "Assets" reads well in the breadcrumb and the pill. Alternatives seen elsewhere: Files (GitBook, Fumadocs), Attachments (Confluence), Downloads (Sphinx's :download: role), File: pages (MediaWiki). "Assets" is the only one that also matches the directory name authors already use.
  • Two URLs per file. The viewer page and the raw file can't share a path on a static host (a file and a directory can't have the same name). Proposal: viewer at /assets/scripts/parse-frontmatter.js/ (a page, trailing slash), raw at /raw/scripts/parse-frontmatter.js (or /assets/_raw/…). Markdown links written as @assets/… are rewritten to the viewer URL; <Asset>'s Download button and "Open raw" use the raw URL.
  • Wide layout, no sidebar/TOC — as the issue asks. The image/video pages use a two-column split instead (stage + details) because a media file has more metadata than prose.
  • Line anchors (#L42, click a line number) come almost free once lines are wrapped in .line spans, which zfb already does. They let a doc link to "the part I'm explaining".
  • Large text files. Cap the inline preview (e.g. 2,000 lines / 500 KB) and show "Showing first N lines — Download for the rest" in the code-note strip, GitHub-style.
  • "Linked from" is the reader's way back. Without it an asset page is a dead end; with it the viewer doubles as an index of where a file is used (MediaWiki's "File usage").
  • Not versioned, not searched, not in the sidebar by default: assets are leaf pages. They should get noindex if the site sets it, and stay out of llms.txt unless opted in.
  • Type detection is by extension (a small map). Unknown extensions → download panel. Text detection could also sniff the first KB for binary bytes so .conf, .env.example, Makefile still preview.

What was borrowed from where

Survey of Docusaurus, VitePress, Starlight/Expressive Code, Nextra, Fumadocs, Mintlify, GitBook, ReadMe, MkDocs Material, Sphinx, GitHub/GitLab, Storybook, Confluence, Notion and MediaWiki (2026-08-30). Verdict: no documentation framework has a per-file viewer page — they all stop at "include the file as a code block" plus a plain link (Sphinx's :download: is the closest, and it is still just a link). The two real models are GitHub/GitLab's blob page and MediaWiki's File: page.

  • Two-URL split — GitHub blob/ vs raw/, MediaWiki File: vs Media:. Links default to the viewer; a distinct raw URL exists for download/hotlinking. → every proto's Download / Open raw buttons.
  • File header bar — GitHub/GitLab: name + "N lines · X KB" left, Raw / Copy / Download right; GitLab collapses the actions into an overflow menu on mobile. → proto B's sticky bar.
  • Type-specific preview with a hard fallback — image / video / PDF / CSV-as-table, else "binary or too large — view raw / download". → protos 03–06.
  • Size ceilings decided up front — GitHub: >1 MB no highlighting, >5 MB raw-only. → the "Large text files" note above.
  • "File usage" list — MediaWiki lists every page that references the file; free in an SSG because the build already knows every referrer. → "Linked from" on every proto.
  • Line-number anchors with ranges — GitHub's #L10-L20. → protos A/B (single line implemented; ranges are a follow-up).
  • Editor-frame file-name tab — Expressive Code puts the file name on the code frame and auto-titles from a file-name comment; Fumadocs infers the icon from the extension. → proto 07's embedded excerpt header.
  • Router escape for raw links — Docusaurus pathname:// keeps a static-file link out of the SPA router. Directly relevant to zudo-doc's client-router-bootstrap: raw/download links must bypass it.
  • Hashed download dir — Sphinx copies :download: targets into _downloads/<hash>/ so duplicate basenames survive. Only matters if viewer URLs don't mirror the source path (here they do).
  • Rendered ↔ source toggle — GitHub's Code/Preview for Markdown and SVG. Worth adding for .md/.svg assets later.

Naming, as other products use it

  • "Static assets" / "public" = the directory (Docusaurus, VitePress, Astro).
  • "Files" = the most common name for the block / page concept (GitBook Files block, Fumadocs <Files>, Confluence Attachments → Files, Notion file block, GitLab "File management", GitHub "blob").
  • "Attachments" = wiki / Confluence; "downloads" = Sphinx; File: namespace = MediaWiki. Nobody leads with "resources".
  • Two workable URL schemes — (1) the issue's naming: viewer at /assets/<path>/, raw moved to /raw/<path>; (2) the survey's split: viewer at /files/<path>/, raw stays at /assets/<path>. (2) keeps every existing /assets/… URL valid and matches how public/ already works; the breadcrumb/pill can still say "Assets" either way.
