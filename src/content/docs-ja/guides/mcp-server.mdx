## 概要

このMCPサーバーを有効にすると、[エージェント向けエクスポート](./agent-export.mdx)を使う2つの読み取り専用ツールが利用できます。新規プロジェクトにはCloudflare Workers向けのデプロイ設定が生成されます。サイトとエンドポイントは**自分のCloudflareアカウント**にデプロイします。静的エクスポートだけならWorkerは不要です。共用ゲートウェイ、AIプロバイダーの認証情報、Durable Object、検索データベースも不要です。

## プロジェクトの作成とデプロイ

イニシャライザーで「MCP」を選ぶか、オプションを指定します。

```bash
pnpm create zudo-doc my-docs --mcp --mcp-deploy cloudflare --yes
cd my-docs
pnpm install
pnpm build
pnpm preview:worker
```

MCPを選んで`agentExport`を省略すると、自動的に有効になります。`mcpDeploy`の省略時は`"cloudflare"`が選ばれます。生成される`zfb.config.ts`には`agentExport: true`、`mcp: true`、Cloudflareアダプターが入ります。`wrangler.jsonc`、`preview:worker`と`deploy`のスクリプト、任意のMCP SDKとデプロイ用依存パッケージも追加されます。Wranglerの`main`は`./dist/_worker.js`を指します。ルートとSDK対応のバンドル解決はパッケージが提供します。ホスト側のWorkerラッパーや共用サービスは生成されません。通常の`--yes`生成では、これらの機能は有効になりません。

安定した引用URLのために、`zfb.config.ts`の`siteUrl`を公開サイトのオリジンに設定します。生成されたWrangler設定を確認し、自分のWorker名とルート・ドメインを選んでください。ローカルで検証した後、所有者がデプロイします。

```bash
wrangler login
pnpm deploy
```

`pnpm deploy`はビルドしてから`wrangler deploy`を実行します。ChatGPTへの接続登録は行いません。Cloudflareアカウント設定、公開ドメイン、プロバイダーの利用には費用がかかる場合があります。公開エンドポイントにはCloudflare標準のレート制限と不正利用対策を利用してください。

## 検証とクライアント接続

`pnpm preview:worker`の実行中に、`<base>/agent/v1/manifest.json`が読めることを確認し、MCPクライアントから`<base>/mcp`に接続します。エンドポイントはセッションを持たないStreamable HTTP POSTを使います。本番環境のGET/HEADは`Allow: POST, OPTIONS`付きの405を返します。ショーケースのプレビューではGET/HEADが静的アセットの404になる場合があります。OPTIONSはCORSプリフライトに応答します。サーバー間クライアントでは`Origin`なしを受け入れ、許可されていない`Origin`がある場合は拒否します。許可されるのはリクエスト自身のオリジンと、`siteUrl`が`http:`または`https:`のURLである場合のそのオリジンです。`docs.example.com:8443`のようにスキームのない`siteUrl`は何も追加しないため、`Origin: null`（サンドボックス化されたiframeや`file:`ページ）は拒否されます。

ChatGPTなどのリモートMCPクライアントには、デプロイ済みのHTTPS URLをカスタムMCP連携として追加します。たとえば`https://docs.example.com/mcp`、`base`が`/manual`なら`https://docs.example.com/manual/mcp`です。接続画面はクライアントごとに異なります。接続後にツールを検出し、具体的な語句で`search`を呼び、返されたIDを`fetch`に渡して、回答が人が読むページのURLを引用することを確認します。実際のChatGPTアカウントでの接続はリポジトリのローカルテストでは未検証です。デプロイ後に確認してください。検証済みの旧プロトコルは2024-11-05のメッセージをセッションなしのPOSTで送る方式です。SSEから始めるクライアントや再開可能なセッションには対応しません。

| ツール | 入力 | 結果 |
| --- | --- | --- |
| `search` | `{query: string}` | 順位付きの`{id,title,url}`を最大10件。該当なしなら`[]` |
| `fetch` | 現在の検索結果から得た`{id: string}` | 選択した項目の`{id,title,text,url,metadata}`全体。存在しなければ明確なnot-found結果 |

人が読むページの`url`は引用に利用できます。`trailingSlash`設定に従うため、リダイレクトなしでページを開きます。長いページには複数の項目IDがあります。関係する各部分を取得するか、ページ全体のMarkdownを開いてください。検索結果のタイトルは分割番号を修飾語の中で一度だけ示します（例: `Read-only MCP server (en · part 1/2)`）。取得した項目は保存されたタイトル`Read-only MCP server (part 1/2)`のままです。ツールは構造化データと同内容のJSONテキストを返し、読み取り専用、冪等、非破壊であると宣言します。AIへの質問、書き込み、履歴、公開用のツールはありません。検索対象はエージェント向けコーパスの全文で、ブラウザー検索の既定の3,000文字を超える部分や日本語も含みます。

## 検出用ドキュメント

Workerは、エンドポイントを説明する読み取り専用のJSONドキュメントを2つ配信します。クライアントはサイト自体からエンドポイントを見つけられます。

| URL | ドキュメント | 公開される条件 |
| --- | --- | --- |
| `<base>/mcp/server-card` | [MCP Server Card](https://github.com/modelcontextprotocol/experimental-ext-server-card)（SEP-2127）、`application/mcp-server-card+json` | `mcp: true`。`base`は問わない |
| `/.well-known/ai-catalog.json` | Server Cardを指すエントリーを1件持つ[AI Catalog](https://github.com/Agent-Card/ai-catalog)、`application/ai-catalog+json` | `mcp: true`かつ`base`が`/` |

Server Cardには、エンドポイントのURL、エンドポイントが受け付けるプロトコルバージョン、`initialize`が返すサーバーバージョンが入ります。`name`は公開ホスト名を逆DNS順にし、`base`を続けたものです。たとえば`https://docs.example.com/`なら`com.example.docs/docs`、`/manual`なら`com.example.docs/manual`です。`title`は`siteName`で、カタログのエントリーも同じ値を`displayName`に持ちます（`siteName`が空ならホスト名）。カードを読まないカタログ読み取り側は、名前がなければエントリーの識別子の末尾しか表示できず、[Agentic Resource Discovery](https://agenticresourcediscovery.org/spec/)（ARD）も名前のないエントリーを受け付けないためです。引用URLと同じく、どちらのドキュメントも`siteUrl`のオリジンを使い、`siteUrl`が空か、`http:`または`https:`のURLでなければリクエストのオリジンを使います。

どちらのドキュメントも、GETとHEADには`Access-Control-Allow-Origin: *`、`Cache-Control: public, max-age=3600`、強い`ETag`を付けて応答します。一致する`If-None-Match`には304を返します。OPTIONSはCORSプリフライトに応答し、それ以外のメソッドは405になります。`/mcp`と同様に、ショーケースのプレビューではGET/HEADが静的アセットの404になる場合があります。

well-known URIはオリジンのルートに属します（RFC 8615）。そのため、サブディレクトリの`base`で公開するサイトはServer Cardだけを配信します。オリジンに独自のAI Catalogがあれば、そこへカードのURLを追加してください。`base`がルートの場合、すべてのページの`<head>`がカタログへリンクします。

```html
<link rel="ai-catalog" href="/.well-known/ai-catalog.json" type="application/ai-catalog+json">
```

`llmsTxt`が有効なら、`llms.txt`のMCPセクションでエンドポイントの次にServer Cardを案内します。

### Cloudflareでの静的アセット用ヘッダー（任意）

Workers Static Assetsは、プリレンダー済みのページとテキストファイルをWorkerより先に配信するため、パッケージからそれらのレスポンスヘッダーは追加できません。アセットディレクトリのルートにある`_headers`ファイル（`dist/_headers`）なら追加できます。このサイトでは`public/_headers`に置いてビルド時にそこへコピーし、カタログと`llms.txt`をHTTPの`Link`ヘッダーで示し、テキストのエクスポートがUTF-8であることを宣言しています。

```text
/
  Link: </.well-known/ai-catalog.json>; rel="ai-catalog"; type="application/ai-catalog+json", </llms.txt>; rel="describedby"; type="text/plain"

/*.txt
  Content-Type: text/plain; charset=utf-8

/agent/v1/pages/*.md
  Content-Type: text/markdown; charset=utf-8
```

ルールのパスは公開URLのパスと照合されるため、`base`を含めてください。各ロケールのホームページには、そのロケールの`llms.txt`を指すルールを追加してください。`charset`がないと、日本語のテキストをISO-8859-1として解釈するHTTPクライアントがあります。これらのルールは静的アセットの404ページにも適用されるため、存在しない`.txt`や`.md`のパスはHTMLの404ページではなくWorkerのプレーンテキストの404を返します。`_headers`のルールは、`/mcp`や2つの検出用ドキュメントのようにWorkerが生成するレスポンスには適用されません。

## 既存プロジェクトへの追加・削除

### プロジェクトを置き換えずにMCPを追加する

MCPに対応した同じリリースの`@takazudo/zudo-doc`と`create-zudo-doc`を使います。対象は**6.0.0以降**です。5.xのリリースはこの手順に対応していません。

必要なら先に[移行ガイド](./migrating-to-zudo-doc-6.mdx)に従って既存プロジェクトを更新し、[静的エクスポート](./agent-export.mdx)を有効にします。コンテンツ、`siteUrl`、`base`、ロケール、バンドル設定、他の機能と共有する依存関係、既存スクリプトを保持します。既存ディレクトリに対してイニシャライザーを実行しないでください。

既存プロジェクトのルートから、インストール済みドキュメントパッケージと**同じ厳密なバージョン**の一時参照プロジェクトを生成します。

```bash
ZUDO_DOC_VERSION=6.0.0
MCP_REFERENCE=$(mktemp -d)/mcp-reference
pnpm dlx "create-zudo-doc@$ZUDO_DOC_VERSION" "$MCP_REFERENCE" --mcp --mcp-deploy cloudflare --yes
mkdir -p scripts
cp -n "$MCP_REFERENCE/scripts/stage-cloudflare-base.mjs" scripts/stage-cloudflare-base.mjs
```

後のリリースを使う場合は`6.0.0`をインストール済みバージョンに置き換えます。参照プロジェクトの`package.json`と`wrangler.jsonc`を確認し、ヘルパーだけをコピーして、デプロイ設定は既存プロジェクトに統合します。同じヘルパーパスが存在する場合は上書きせず比較してください。検証が終わるまで参照プロジェクトを残します。これにより、作成済みの設定を置き換えずに、バージョンに合ったビルド処理を入手できます。

参照プロジェクトに記載されたMCP依存関係をインストールします。現在対応する組み合わせは次のとおりです。

```bash
pnpm add @modelcontextprotocol/sdk@1.32.2 @takazudo/zfb-adapter-cloudflare@5.2.2
pnpm add -D wrangler@4.162.0
```

Wrangler 4.162.0 は MCP スキャフォールド専用のピンです。MCP を有効にしない Cloudflare プロジェクトには入りません。`@cloudflare/workers-types` 5.20261110.1 はこのリポジトリのワークスペース devDependency であり、生成される `package.json` に書き込まれるピンではありません。アダプターモードの `zfb preview` は Wrangler 4.85.0 を下限として扱い、それより新しい版はテスト済みベースラインを上回るとログして続行します。

アダプターはプロジェクトが対応するzfbバージョンに合わせます。既存の`zudoDoc({ ... })`内で、他の設定を維持して次のフィールドを有効にします。

```ts
agentExport: true,
mcp: true,
adapter: "@takazudo/zfb-adapter-cloudflare",
```

`siteUrl`は`https://docs.example.com`のような正規オリジンのままにします。ルート配置では`base`を省略するか`/`にし、サブディレクトリ配置では`base: "/manual"`を維持します。MCPが有効なとき、パッケージは既存バンドル設定を保持しながら、SDKに必要な`module`と`main`の解決フィールドを加えます。

自分のDNSに使えるWorker名を選んで`wrangler.jsonc`を追加または統合します。他の機能で使うバインディングやルートを保持してください。現在の生成済み構成は次の形です。

```json
{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "name": "my-docs",
  "main": "./dist/_worker.js",
  "compatibility_date": "2024-12-01",
  "compatibility_flags": ["nodejs_compat"],
  "assets": {
    "directory": "./dist",
    "binding": "ASSETS",
    "not_found_handling": "404-page",
    "run_worker_first": false
  }
}
```

`&& node scripts/stage-cloudflare-base.mjs`を、後処理も含めた**既存のビルドコマンド全体が成功した後**に追加します。たとえば既存の`zfb build && node scripts/postbuild.mjs`は次の形になります。

```json
{
  "scripts": {
    "build": "zfb build && node scripts/postbuild.mjs && node scripts/stage-cloudflare-base.mjs",
    "preview:worker": "wrangler dev",
    "deploy": "pnpm build && wrangler deploy"
  }
}
```

`scripts`オブジェクトを置き換えずに統合します。既存のpreviewまたはdeployスクリプトがある場合は保持し、MCPの検証・デプロイには別の名前を選びます。`.gitignore`に`.wrangler/`がなければ追加します。ヘルパーはエクスポート済みマニフェストのbaseを読みます。ルート配置では何も移動せず、`/manual`配置ではプリレンダリング済みページ、llmsファイル、ブラウザーアセットを`dist/manual/`配下に配置してWranglerが提供できるようにします。Workerエントリーは`dist/_worker.js`のままです。移動したり、エクスポートをラップしたりしないでください。

以下のllmsパスは`llmsTxt: true`の場合だけ確認します。MCPを有効にしても、この独立したエクスポートは有効になりません。

`pnpm build`と`pnpm preview:worker`を実行します。ルート配置では`/docs/`、`/llms.txt`、`/agent/v1/manifest.json`、`/mcp`を、`/manual`配置では`/manual/docs/`、`/manual/llms.txt`、`/manual/agent/v1/manifest.json`、`/manual/mcp`を確認します。実際のコンテンツページと参照先のJS/CSSを開き、SDKクライアントで`search`/`fetch`を検出し、ENとJAのコンテンツを検索し、返されたIDをfetchして引用用の人間向けURLを開きます。マニフェストのMarkdownと項目URLも確認してください。正規引用URLには公開オリジンとbaseが必要です。ローカルランタイムでは、表示されたオリジンの同じパスで確認できます。この検証が終わってから、前述の手順でデプロイとアカウント接続を行います。

### MCPを削除して静的エクスポートを残す

`mcp: false`にするかフィールドを削除し、`agentExport: true`と既存のサイト・base・ロケール設定を保持します。Cloudflareアダプター設定は**他の機能で不要な場合だけ**削除します。Cloudflare設定がすべてMCP専用だった場合、完全な静的プロジェクトに戻す手順は次のとおりです。

1. `build`から追加した`&& node scripts/stage-cloudflare-base.mjs`だけを削除し、元のコマンドと後処理を保持します。不要になったヘルパーを削除します。
2. MCP専用のpreview/deployスクリプトと`wrangler.jsonc`を削除します。共有していた場合はMCP用の追加部分だけを削除します。`.wrangler/`のignore指定は、残るツールが使わない場合だけ削除します。
3. `pnpm remove @modelcontextprotocol/sdk @takazudo/zfb-adapter-cloudflare wrangler`は、残るすべての機能で使わない依存関係に対してだけ実行します。共有するアダプター、SDK、デプロイツールは保持します。
4. `pnpm build`を実行します。完全な静的出力にはMCPルートと`dist/_worker.js`がなく、マニフェスト、項目JSON、ページごとのMarkdownが`dist/<base>/agent/v1/`配下に残ることを確認します。有効なllmsファイルは`dist/llms.txt`と`dist/<locale>/llms.txt`に戻り、リンクには正規オリジンとbaseが保持されます。静的ページ、llmsファイル、ブラウザーアセットには、静的ホストの通常のbase配置方式を使います。削除したヘルパーはWrangler専用です。既存の静的ホスト公開手順で再ビルドした出力を公開し、古いWorkerデプロイを置き換えてエンドポイントを公開しなくします。

MCPの無効化だけでは、公開静的コーパスは削除されません。それも不要な場合は`agentExport`を別途無効にして再ビルドし、公開成果物を置き換えて古い`/agent/v1/`ファイルを削除します。独立した`llmsTxt`設定はドキュメントを公開し続ける場合があります。その公開も不要なら無効にしてください。

## 上限と公開時の安全性

検索クエリの上限はUTF-16コード単位で500、空のクエリは無効です。各項目の本文は最大8,000 UTF-16コード単位で、サロゲートペアの途中では分割しません。最終JSON-RPC応答は131,072 UTF-8バイト、POST本文は65,536バイトが上限です。マニフェストは8 MiB、エージェント検索インデックスは16 MiBおよび10,000項目が上限です。超過時は本文を黙って切らず、明示的に失敗します。サーバーは現在のマニフェストの項目IDと成果物ハッシュを検証し、異なるビルドの混在を防ぎます。

エンドポイントと静的ファイルは**公開ドキュメント**を提供します。`robots.txt`、`noindex`、`unlisted`、`search_exclude`は認証ではありません。保護された資料にコーパスを有効化しないでください。将来の非公開モードでは、`/mcp`と静的成果物の両方を保護する必要があります。取得した文書は信頼できないデータであり、コマンド実行や追加権限の根拠にはなりません。MCPが不要なら、ブラウザークライアントにサイトURLと[llms.txt](./llms-txt.mdx)、または生成されたMarkdown URLを明示的に渡してください。ホームページURLだけでは、クライアントが`llms.txt`を読むとは限りません。
