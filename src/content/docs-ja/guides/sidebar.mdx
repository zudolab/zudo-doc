## アイテムの並び順

カテゴリ内のページは`sidebar_position`フロントマターフィールドでソートされます。小さい値ほど先に表示されます。

`sidebar_position`がないページはデフォルト値`999`が適用され、カテゴリの末尾にファイル名のアルファベット順で表示されます。

```mdx
---
title: My Page
sidebar_position: 3
---
```

<Tip>

ページの順序を制御するために、`sidebar_position`を常に明示的に設定してください。設定しないとページはアルファベット順にソートされ、意図した読み順と一致しない場合があります。

</Tip>

## カテゴリの並び順

サイドバー内のカテゴリは**インデックスページ**（`index.mdx`）の`sidebar_position`で順序付けされます。インデックスページ（または従来の`_category_.json`）で位置が指定されていないカテゴリは、位置`999`として扱われ、同じ位置どうしはディレクトリ名のアルファベット順で並びます。

例えば、「Getting Started」を最初に、「Guides」を2番目にするには：

```
getting-started/index.mdx  → sidebar_position: 0
guides/index.mdx            → sidebar_position: 1
reference/index.mdx         → sidebar_position: 2
```

## カテゴリインデックスページ

ディレクトリ内に`index.mdx`を作成すると、カテゴリにランディングページが付与されます。サイドバーのカテゴリ名がこのページへのクリック可能なリンクになります。

一般的なカテゴリインデックスページでは`<CategoryNav />`コンポーネントを使用して、カテゴリ内のすべてのページを自動的にリスト表示します：

```mdx
---
title: Guides
sidebar_position: 1
---

Explore our guides to learn about zudo-doc features.

<CategoryNav category="guides" />
```

`<CategoryNav />`コンポーネントは、カテゴリ内のすべてのページ（インデックス自体を除く）へのリンクのグリッドを`sidebar_position`でソートしてレンダリングします。

### リンク付きの行と見出しだけの行

カテゴリの行の動作は、インデックスページによって決まります。

| カテゴリディレクトリ | サイドバーの行 | ルート |
| --- | --- | --- |
| `index.mdx` を書いた場合 | ランディングページへのリンク付きの行。タイトル、位置、説明はフロントマターから取得 | 書いたページ |
| `index.mdx` はないがページを含む場合 | 子を一覧にする生成されたインデックスページへのリンク付きの行。ラベルはディレクトリ名から取得 | 生成された自動インデックスのルート |
| `index.mdx` に `category_no_page: true` がある場合 | 展開・折りたたみだけを行う見出しの行 | なし |

ランディングページに意図した内容、ラベル、位置を与えられるため、すべてのカテゴリで `index.mdx` を書くことを推奨します。インデックスがなくても、カテゴリがトグル専用になるわけではありません。ページを持たない見出しにしたい場合は `category_no_page: true` を使ってください。

サイドバーは、行に `href` があればリンクとして描画します。`hasPage` フラグは、その行に書かれたページがあるかどうかを示すだけなので、「リンクかどうか」の判定には使えません。生成された自動インデックスの行や `type: "link"` アイテムは `hasPage: false` ですが、リンクになります。[ノートトレイ](./note-tray.mdx)はより厳しく、表示されるルート付きの `index.mdx` が必要です。

## デフォルトの展開・折りたたみ

現在のページを含むカテゴリは常に展開されます。`sidebar_initial_expansion`を省略すると、通常のカテゴリは従来どおり展開されます。TypeScriptで明示した`collapsed`の値は個別の例外として維持されます。

カテゴリの`index.mdx`に`sidebar_initial_expansion: collapsed`または`expanded`を設定すると、その配下に初期状態を継承できます。最も近いカテゴリの設定が適用され、現在のページに設定した値がそれを上書きします。この設定は展開状態を制御し、`initialPath`は引き続きサイドバーの初期表示範囲を制御します。

```mdx
---
title: Guides
sidebar_position: 1
sidebar_initial_expansion: collapsed
---
```

セッション内に保存されるのは、読者が明示的に行った展開・折りたたみの操作だけです。現在のページの祖先カテゴリを自動で開く動作（ページ到着時。戻る・進むやソフトナビゲーションを含み、画面幅を問いません）や、選択・拡大した表示範囲のルートを開く動作は保存されません。現在のページを含むカテゴリも折りたたむことができ、そのページでは折りたたまれたままになります。ハッシュの変更、フィルターへの入力、同じページの再読み込みでも再び開きません。別のページへ移動すると、そのページへの経路が再び開かれます。関係のない枝での選択は維持されます。

復元操作は現在のページの著者設定に展開状態と表示範囲を戻します。実際の状態がその基準と異なる場合にのみ復元ボタンが表示されます。最上位の表示範囲ではツールバー全体が非表示になり、各カテゴリの枝だけを表示する操作は引き続き利用できます。

<Note>

以前のバージョンで保存された状態には、自動の展開と手動の展開が混在していました。そのため、アップグレード後の最初の読み込みで以前の展開・折りたたみ状態を一度だけ破棄します。保存された表示範囲とフィルターの文字列は維持されます。この処理は繰り返されません。

</Note>

## サイドバーラベル

`sidebar_label`フロントマターフィールドを使用して、ページタイトルとは異なるラベルをサイドバーに表示できます。完全なタイトルがサイドバーには長すぎる場合に便利です。

```mdx
---
title: Getting Started with zudo-doc Installation
sidebar_label: Installation
sidebar_position: 2
---
```

<Tip>

`sidebar_label`はサイドバーにのみ影響します。ページタイトルと見出しには引き続き`title`が使用されます。

</Tip>

## ディレクトリ構造

`src/content/docs/`内のディレクトリがサイドバーカテゴリになります。ディレクトリ名はkebab-caseからTitle Caseに自動的に変換されます。

```
src/content/docs/
  getting-started/         → "Getting Started"
    index.mdx              → category index (sidebar_position: 0)
    introduction.mdx       → sidebar_position: 1
    installation.mdx       → sidebar_position: 2
    writing-docs.mdx       → sidebar_position: 3
  guides/                  → "Guides"
    index.mdx              → category index (sidebar_position: 1)
    configuration.mdx      → sidebar_position: 1
    frontmatter.mdx        → sidebar_position: 2
```

## ネストカテゴリ（サブグループ）

カテゴリディレクトリ内にサブディレクトリを作成すると、サイドバーにネストされた折りたたみグループが生成されます。各サブディレクトリに `index.mdx` を置くと、グループの行が実際のランディングページへのリンクになります。

```
src/content/docs/
  methodology/
    index.mdx               → title: Methodology, sidebar_position: 1
    architecture/
      index.mdx             → title: Architecture, sidebar_position: 1
      bem-strategy.mdx
      component-first.mdx
    design-systems/
      index.mdx             → title: Design Systems, sidebar_position: 2
      tight-token.mdx
      two-tier-size.mdx
```

自動生成のサイドバーは実際のカテゴリノードを維持します。各グループの行は開閉ボタンとは別のリンクになり、ランディングページが子として重複することはありません。

```
Methodology            (linked)
▸ Architecture         (linked, collapsible)
    BEM Strategy
    Component First
▸ Design Systems       (linked, collapsible)
    Tight Token
    Two-Tier Size
```

これにはサイドバー設定は不要です。サブディレクトリの `index.mdx` に `category_no_page: true` を追加するのは、そのグループを自身のページを持たない見出しにしたい場合だけです。

ツリーは再帰的で、決まった深さの制限はありません。浅く保つのは読みやすさのための推奨です。セクションが深くなったら、別のヘッダーセクションへの分割を検討してください。ファイルを変えずにセクションのリンク付きグループを一段浅く表示するには、[表示範囲のレシピ](#ツリーを広げる-表示範囲のレシピ)を参照してください。

## サイドバー設定

ほとんどのサイトは自動生成のツリーで足ります。代わりに設定オブジェクトでセクションを記述することもでき、`sidebarsConfig` chrome スロットからバインドします。設定ファイルは自動では読み込まれません。

<Warning title="サイドバーデータ binding が必要です">

`sidebarsConfig` のデフォルトは `{}` で、すべてのセクションがファイルシステムの自動生成を使います。`chromeBindingsModule` を設定をバインドするモジュールへ向けてください。新しいルートスタブはそれをすでに消費するため編集しません。詳しくは [Custom Components](./custom-components.mdx) と [ホストクロームバインディング](../reference/host-chrome-bindings.mdx)を参照してください。

</Warning>

`headerNav`内の`categoryMatch`値と正確に一致するキーを持つ設定を作成し、バインドします。

```ts title="src/sidebars.ts"
import type { SidebarsConfig } from "@takazudo/zudo-doc/sidebar-utils";

const sidebars: SidebarsConfig = {
  guides: [
    "guides/introduction",
    { type: "doc", id: "guides/sidebar", label: "Sidebar" },
    { type: "link", label: "Project site", href: "https://example.com" },
    {
      type: "category",
      label: "Architecture",
      collapsed: true,
      sortOrder: "asc",
      items: [{ type: "autogenerated", dirName: "guides/architecture" }],
    },
  ],
};

export default sidebars;
```

```ts title="src/chrome-bindings.ts"
import { defineChromeBindings } from "@takazudo/zudo-doc/chrome-bindings";
import sidebars from "./sidebars";

export const chromeBindings = defineChromeBindings({
  sidebarsConfig: sidebars,
});
```

```ts title="zfb.config.ts"
export default defineConfig(
  zudoDoc({
    chromeBindingsModule: "./src/chrome-bindings.ts",
  }),
);
```

一致するキーがないセクションや、空の配列を指定したセクションは、ファイルシステムの自動生成にフォールバックします。

### アイテムの意味

各アイテムは自動生成ツリーから行を作ります。ページを作ったり URL を変えたりするものはありません。

| アイテムまたはフィールド | 結果 |
| --- | --- |
| `"doc/slug"` または `{ type: "doc", id, label? }` | 実際のドキュメントを**葉**として選びます。子は取り除かれます。存在しない id は飛ばされます。 |
| `{ type: "link", label, href }` | 任意の URL へのリンク付きの行です。 |
| `{ type: "category", label, items, collapsed?, sortOrder? }` | 列挙したアイテムを含む、`href` のない**合成の見出し**です。 |
| `{ type: "autogenerated" }` | 渡されたツリー全体を、ルートの行も含めて使います。 |
| `{ type: "autogenerated", dirName }` | そのディレクトリの**子**を表示ツリーに挿入します。ディレクトリの行自体は表示されませんが、ツリーを広げる操作では親として扱われます。 |
| `initialPath` | URL のセグメントではなく、**解決済みの表示ツリー**に対するゼロ始まりのインデックスです。 |
| `initialPathMode: "node"` | 選んだ行とその子が基準になります。 |
| `initialPathMode: "children"`（デフォルト） | 選んだ行の子だけが基準になります。 |
| `scopeRoot` | **ツリーを広げる**が到達できる最も高いツリーです。階層を作ったり、`initialPath` の数え方を変えたりはしません。 |
| `sidebar_initial_expansion`（フロントマター） | どの枝を最初に開くかを決めます。開閉は表示範囲とは独立しています。 |

`SidebarCategory` には `link`、`href`、`id`、ランディングページを指定するプロパティはありません。合成カテゴリの見出しをページへリンクさせることはできません。

### 合成カテゴリによる見出しだけのグループ

`type: "category"` は、グループを意図的にランディングページのない見出しにしたい場合に使います。たとえば、自身のページを持たないラベルの下にいくつかのページをまとめる場合です。

```ts title="src/sidebars.ts"
import type { SidebarsConfig } from "@takazudo/zudo-doc/sidebar-utils";

const sidebars: SidebarsConfig = {
  methodology: [
    "methodology",
    {
      type: "category",
      label: "Architecture",
      items: [{ type: "autogenerated", dirName: "methodology/architecture" }],
    },
    {
      type: "category",
      label: "Design Systems",
      items: [{ type: "autogenerated", dirName: "methodology/design-systems" }],
    },
  ],
};

export default sidebars;
```

次のように、リンクではない見出しを持つ 2 レベルで表示されます。

```
Methodology            (leaf link)
▸ Architecture         (heading only)
    BEM Strategy
    Component First
▸ Design Systems       (heading only)
    Tight Token
    Two-Tier Size
```

- 文字列 `"methodology"` はカテゴリインデックスを**葉のリンク**として参照します。ネイティブの子は取り除かれるため、構造は設定が決めます。
- `dirName` は各サブディレクトリの記事を、サブディレクトリの行なしで取り込みます。
- Architecture と Design Systems のランディングページには、サイドバーからたどれなくなります。

<Warning title="合成カテゴリはランディングページにリンクしません">

ランディングページを合成カテゴリの中に置いても、見出しはそのページへのリンクになりません。次の設定は、リンクのない「Basics」見出しの最初の子に「Basics」リンクがある表示になります。

```ts
{
  type: "category",
  label: "Basics",
  items: ["reference/basics", "reference/installation", "reference/configuration"],
}
```

ランディングページを持つグループでは、実際のカテゴリノード（上の自動生成ツリー）を残すか、[`initialPath`](#ツリーを広げる-表示範囲のレシピ)で浅い表示を選んでください。ページがディスク上で兄弟になっていて URL を変えられない場合は、[編集上のナビゲーション](./editorial-navigation.mdx)を参照してください。

</Warning>

### このショーケースの設定

パッケージの `sidebarsConfig` のデフォルトは `{}` です。このリポジトリの `src/config/sidebars.ts` は `src/chrome-bindings.tsx` でバインドしているショーケースの設定で、各ヘッダーセクションに `{ items: [], scopeRoot: "configured" }` を指定しています。どのセクションもファイルシステムのツリーを使い、**ツリーを広げる**は他のヘッダーセクションまで広がらず、そのセクションで止まります。

## ソート順（昇順・降順）

デフォルトでは、カテゴリ内のアイテムは昇順（`sidebar_position`が小さい順、次にアルファベット順）でソートされます。カテゴリの `index.mdx` の `category_sort_order` フロントマターフィールドを使用してカテゴリごとに降順に変更できます：

```mdx title="changelog/index.mdx"
---
title: Changelog
sidebar_position: 10
category_sort_order: "desc"
---
```

`category_sort_order`が`"desc"`の場合、アイテムは逆順でソートされます — positionが大きい順、次に逆アルファベット順。これは日付ベースのコンテンツ（変更履歴、リリースノート）で、最新のアイテムを上部に表示したい場合に便利です。

ノートトレイでは、同じフィールドがすべての並び順を決めます。指定した向きは、サイドバー、`<NoteTrayIndex>`、前・次ページャー、ホームページのブロックで安定したrankを並べる向きを制御しますが、rankの値自体は変わりません。`note_tray_sidebar: "year"`または`"month"`ではグループもその向きの時系列で並び、グループ内のアイテムはrank順になります。日付グループと読み順が一致するよう、`sidebar_position`は`date`と同じ時系列で付けてください。詳しい設定は[ノートトレイ](./note-tray.mdx)を参照してください。

<Note>

`_category_.json` は引き続き動作しますが、zfb のビルド警告が発生します。新しいカテゴリには `index.mdx` のフロントマターを使用してください。

</Note>

バインドしたサイドバー設定では、合成カテゴリに`sortOrder`を設定することもできます：

```ts
{
  type: "category",
  label: "Releases",
  sortOrder: "desc",
  items: [
    { type: "autogenerated" },
  ],
}
```

<Tip>

変更履歴スタイルのカテゴリでは、`sortOrder: "desc"`と日付プレフィックスのファイル名（例：`2026-03-10-release.mdx`）を組み合わせることで、`sidebar_position`を手動設定しなくても自動的に最新順に並べられます。

</Tip>

## 並び順の推奨事項

- 予測可能な順序のためにすべてのページに`sidebar_position`を設定する
- カテゴリインデックスページには`sidebar_position: 0`を使用する
- 各カテゴリ内のページには連番（1, 2, 3...）を使用する
- 後でページを挿入する予定がある場合は番号に間隔を空ける（例：10, 20, 30）
- 最新順のカテゴリには`index.mdx`で`category_sort_order: "desc"`を使用する
- ノートトレイでは`note_tray_sidebar: "index"`、`"year"`、`"month"`から選択する。yearとmonthでは全アイテムに日付が必要

## ツリーを広げる

フィルターの下のコントロールは、記事、読書位置、目次を変えずに表示するナビゲーションを切り替えます。**ツリーを広げる**は編集上の親へ一段ずつ移動します。表示できる最上位では範囲ツールバー（ツリーを広げる・現在のページのツリーに戻す）全体が非表示になり、無効化されたボタンやヒントは表示されません。カスタム設定の複数ルートが最上位になる場合もあります。

表示範囲（ツリーのどの部分を表示するか）は、開閉（どの枝を開くか）や構造（どの行が親か）とは別のものです。各カテゴリーには独立した**この枝だけを表示**ボタンがあります。カテゴリーのリンクはページを開き、開閉ボタンは子項目を開閉します。別の範囲を表示している間は**現在のページのツリーに戻す**が表示され、現在のページに設定されたルートと順序を復元します。モバイルのドロワーでも範囲操作では閉じず、ページリンクでは通常どおり閉じます。

範囲を変えてもフィルターは保持されます。カテゴリーが一致すれば子孫を保持し、子孫が一致すればその祖先を保持します。枝の開閉状態は広げる操作と枝の選択で保持されます。復元操作は設定された基準（`initialPathMode: "node"` を含む）に戻し、選択中の範囲と保存された展開・折りたたみの選択を消去し、フィルターの文字列は維持したまま現在のページへの経路を開きます。フィルターがそのページを除外している場合は解除してください。デスクトップのサイドバーとモバイルのドロワーは同時に更新されます。ツリーは再帰的で、深さの制限はありません。

範囲はセッション内の一時状態です。`initialPath` と `initialPathMode` が決めるのは、初回表示と復元時の基準だけです。編集コンテキスト（同じ完全な `items` ツリーに同じ `contextId` を指定したもの、または自動生成ツリー）を共有するセクションは保存状態も共有するため、読者が選んだ拡大・選択の範囲は復元するまでそれらのページで維持されます。選択範囲内のリンクでは範囲を保持し、別の枝への移動では最も近い共通の親まで広げます。言語、バージョン、独立したドキュメントのコンテキストを変えると移動先の設定に戻ります。構造変更後の古い範囲は無効になります。保存された範囲の表示が現在のページの基準と同じ場合は基準として扱われ、復元ボタンは表示されません。URLや修飾キー付きクリック、新しいタブの動作は従来どおりです。

### 編集上の親を明示する

既存の配列設定は初期表示を維持します。ローカルな表示範囲の外側に親を指定するにはオブジェクト形式を使います。`items` は編集上のツリー全体を定義し、`initialPath` は解決・並び替え後のツリーにおけるゼロ始まりのインデックスで、初期表示する子項目の親を指定します。次の例では初期表示が Background と Border、その上が Surfaces & borders、さらに上が Utility reference です。これらのグループはURLに含まれている必要がありません。これらは合成の見出しだけの行です。実際のランディングページを親にするには、[編集上のナビゲーション](./editorial-navigation.mdx)を参照してください。

```ts title="src/sidebars.ts"
import type { SidebarsConfig } from "@takazudo/zudo-doc/sidebar-utils";

const sidebars: SidebarsConfig = {
  utilities: {
    contextId: "utility-reference",
    items: [
      {
        type: "category",
        label: "Utility reference",
        items: [
          {
            type: "category",
            label: "Surfaces & borders",
            items: ["utilities/background", "utilities/border"],
          },
        ],
      },
    ],
    initialPath: [0, 0],
  },
};

export default sidebars;
```

上の設定例と同様に `chromeBindings.sidebarsConfig` へ渡します。`contextId` は省略可能です。同じ完全な `items` ツリーを共有し、異なる `initialPath` を使うセクションには同じ値を指定します。言語、バージョン、構造のリビジョンは自動的に追加されます。不正なパスでは親を推測せず、ビルドが失敗します。

#### ノード自体を選択する

`initialPathMode` は `initialPath` が何を選ぶかを決めます。既定値の `"children"` では、選択したカテゴリの子項目を表示します。`"node"` では、選択したノード自体が基準になり、その行（ページを持つセクションは概要ページへのリンクを維持）と子項目を表示します。`navigation.roots` には引き続き編集上のツリー全体が含まれるため、ツリーを広げると対象の実際の親へ、さらにその上へと移動します。親の行が重複したり、存在しない親が作られたりすることはありません。

```ts title="src/sidebars.ts"
import type { SidebarsConfig } from "@takazudo/zudo-doc/sidebar-utils";

const sidebars: SidebarsConfig = {
  wind: {
    items: [{ type: "autogenerated", dirName: "wind" }],
    // Utility reference → Surfaces & borders
    initialPath: [0, 0],
    initialPathMode: "node",
  },
};

export default sidebars;
```

自動生成されたツリー Wind → Utility reference → Surfaces & borders → Background color で、`initialPath` が Surfaces & borders を指す場合を考えます。Background color のページでは、node モードは最初に Surfaces & borders（概要ページへのリンク付き）とその配下のページを表示し、ツリーを広げると Utility reference、続いて Wind を表示します。children モードでは最初に Surfaces & borders 配下のページだけを表示し、最初にツリーを広げると Surfaces & borders の行が加わります。

`initialPath` がない、または空の場合は、どちらのモードでも解決済みのツリー全体を表示します。node モードでは、葉のページで終わる有効なパスも指定でき、そのページだけを表示します。不正なインデックスや、それ以外の `initialPathMode` の値はビルドを失敗させます。どちらのモードもデスクトップのサイドバーとモバイルのドロワーで同じように動作します。

`items` が空のオブジェクト形式（`items: []`）では、エントリを省略した場合と同じくカテゴリで絞り込んだ自動生成ツリーを使い、そこに `initialPath` と `initialPathMode` を適用します。`buildSidebarForSection` と `buildSidebarNavigation` は同じ結果になり、不正なパスやモードも同様に失敗します。エントリの省略や空の配列は、従来どおり自動生成ツリーのみを使います。

#### 広げる範囲の上限

`scopeRoot` は **ツリーを広げる** が到達できる最も高いツリーを決めます。省略するか `"editorial"` を指定すると、上で説明した動作のままです。カテゴリで絞り込んだ自動生成ツリーは自動生成フォレスト全体まで広げられ、`autogenerated` のディレクトリも実際の祖先まで広げられます。`"configured"` では、記述したフォレストがその上限になります。

- `items: []` は、カテゴリで絞り込んだ自動生成ツリーが上限です。`"!"` のフォールバックも同じです。
- `dirName` のある `autogenerated` が 1 件のときは、そのディレクトリが上限です。概要行と項目の識別子はそのままで、`initialPath` はそのディレクトリの中のインデックスを数えます。
- `dirName` のない `autogenerated` が 1 件のときは、もともとフォレスト全体を要求しているので、上限を設けても縮小しません。
- 明示的な項目が複数あるときは、そのキュレーションされたフォレストが上限です。

`initialPath` と `initialPathMode` が決めるのは、これまでどおり初回表示と復元時の基準だけです。上限に達すると範囲ツールバーは表示されません。それ以外の `scopeRoot` の値はビルドを失敗させます。配列のエントリと、エントリの省略は editorial のままです。

```ts title="src/sidebars.ts"
import type { SidebarsConfig } from "@takazudo/zudo-doc/sidebar-utils";

const sidebars: SidebarsConfig = {
  reference: { items: [], scopeRoot: "configured" },
  wind: {
    items: [{ type: "autogenerated", dirName: "wind" }],
    initialPath: [0, 0],
    initialPathMode: "node",
    scopeRoot: "configured",
  },
};

export default sidebars;
```

Reference のページでは、サイドバーは Reference とそのページを表示し、他のヘッダーセクションへは広げません。焦点を絞った入れ子の枝は、Reference まで広げて戻すことができます。Wind の例では、node モードは Surfaces & borders から始まり、ツリーを広げると Utility reference、続いて Wind まで到達して、そこで止まります。

`autogenerated` は表示から省いたディレクトリルートの由来を保持します。手書きのグループ構造が優先され、同じラベルや同じページへの複数リンクも別々の項目として識別されます。共通の親を持たないカスタムの複数ルートでは、そこで広がりが止まります。ヘッダーのドロップダウングループはドキュメントの祖先にはなりません。

### 表示範囲のレシピ

`initialPath` を選ぶ前に、表示ツリーを書き出してください。以下の例は次のファイルシステムを前提にしています。

```
guides/                    (index.mdx, linked)
├── setup/                 (index.mdx, linked)
│   └── install.mdx
└── writing/               (index.mdx, linked)
    └── pages.mdx
reference/                 (index.mdx, linked)
├── basics.mdx
└── commands.mdx
```

**デフォルトのファイルシステムナビゲーションは、実際のセクションルートをすでに維持しています。** `guides` のエントリがなければ、Guides のページには Guides の行とその子が表示されます。ラップする必要はありません。

```
Guides                     (linked)
├── Setup                  (linked)
│   └── Install
└── Writing                (linked)
    └── Pages
```

**ツリーを広げる範囲をセクションで止める**場合も同じツリーを使います。`{ items: [], scopeRoot: "configured" }` は上のツリーをそのまま表示し、**ツリーを広げる**は Guides の外へ出ません。

**リンク付きの子グループを同列に表示する。** `guides` でカテゴリを絞り込んだツリーには Guides だけが含まれるため、`[0]` は Guides です。children モードではリンク付きのグループが最上位に表示され、ツリーを広げると Guides の行に戻ります。

```ts
guides: { items: [], initialPath: [0] }
```

```
Setup                      (linked)
└── Install
Writing                    (linked)
└── Pages
```

**渡したルート自体を選ぶ。** 表示ツリーが自分で渡したフォレスト、たとえば[編集上のナビゲーション](./editorial-navigation.mdx)のルートが 1 つの `[Reference]` フォレストの場合、`dirName` なしの `autogenerated` はそのフォレストを維持し、node モードは Reference をその子と一緒に選びます。

```ts
reference: { items: [{ type: "autogenerated" }], initialPath: [0], initialPathMode: "node" }
```

```
Reference                  (linked)
├── Basics
└── Commands
```

これが正しいのは、渡したツリーのルートが 1 つだからです。ネイティブのツリーでは `{ type: "autogenerated" }` はサイト全体のフォレスト `[Guides, Reference]` なので、同じ定義は Guides を選びます。

<Caution title="dirName は [0] の意味を変えます">

`{ items: [{ type: "autogenerated", dirName: "reference" }], initialPath: [0] }` は Reference を選び**ません**。`dirName` は Reference の子を挿入するため、表示ツリーは `[Basics, Commands]` となり、`[0]` は Basics です。children モードでは Basics の子（Basics はページなので何もなし）を表示し、node モードでは Basics だけを表示します。

</Caution>

`[0]` はグローバルなツリーに対する普遍的なインデックスではありません。常に、そのセクションのアイテムが作る表示ツリーから数えてください。

独自の統合では `@takazudo/zudo-doc/sidebar-utils` の `buildSidebarNavigation` を呼び、返された `nodes` と `navigation` を `SidebarTree` または `SidebarToggle` に渡せます。`buildSidebarForSection` と `nodes` だけを渡す形式も引き続き利用でき、後者では範囲コントロールを追加せず従来のツリーを表示します。

### クライアントへ渡すナビゲーションデータ

標準のヘッダーとサイドバーファクトリーは、サイドバーアイランドが必要とするフィールドだけをコピーします。ページの説明文はカテゴリ表示用のサーバーナビゲーションデータに残りますが、ブラウザーへ送る表示中のノードと広い範囲のツリーからは再帰的に除かれます。モバイルの `sidebarNodes` 配列とコールバックの戻り値は、URL を書き換えずにコピーされます。オブジェクトの同一性は保持しません。

独自のホストでは、`SidebarTree` または `SidebarToggle` のアイランドを作る前に `@takazudo/zudo-doc/sidebar` の `toSidebarClientData(nodes, navigation)` を呼び、戻り値を SSR とハイドレーションの両方に渡せます。このヘルパーはフィールドを選ぶ前に入力を検証し、項目の識別子、ツリー構造、展開の初期値、既存のナビゲーションコンテキスト ID を維持します。説明文の変更は引き続きコンテキスト ID に影響する場合があります。これは転送データの削減であり、プライバシー境界や表示範囲の保存方式を変更するものではありません。
