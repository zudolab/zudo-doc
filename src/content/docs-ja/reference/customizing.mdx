zudo-docはクローズドなパッケージとして提供されます。コンポーネントは`node_modules`内に存在し、スタイルシートはコンパイル済みで、レンダリングパイプラインは固定されています。しかし、zudo-docを使って構築されるプロジェクトは、ちょっとした色の調整からフルカスタムのヘッダーまで、さまざまなブランディングニーズを持っています。このページでは、利用可能なすべてのカスタマイズレバーを軽量なものから侵襲的なものの順に並べて示します。変更をエンジニアリングしすぎることも、足りなすぎることもなく、適切なツールを選べるようにするためです。

## 判断フロー表

| レバー | スコープ | 使うとき | 制限 |
| --- | --- | --- | --- |
| **1. グローバル `@theme` トークン** | サイト全体 | 変更がすべての場所に適用される場合（全カラー、全テキスト、全スペーシング） | 特定のコンポーネントだけを変えることはできない |
| **2. `--zdc-*` コンポーネントトークン** | コンポーネント単位 | グローバルなデフォルト値とは異なる、見出し・プロのフォントやレイアウト寸法が必要な場合 | サポートされているトークンセットのみ |
| **3. 設定（Settings）** | 機能のオン/オフと設定値 | 機能を有効・無効にする場合。TOCの深さやサイドバーの動作、ナビゲーション構造を調整する場合 | 設定が公開している範囲を超えて視覚的なレンダリングを変更することはできない |
| **4. `doclayout` スロット** | マークアップ/スクリプト挿入 | レイアウトの特定位置にクロム（バナー、アナリティクス、追加のナビアイテム、カスタムスクリプト）を追加する場合 | レイアウトに追加するのみ。既存コンポーネントの再スタイリングはできない |
| **5. コンポーネントイジェクション** | ソース全体の制御 | 特定コンポーネントの完全な視覚的コントロールが必要な場合 | イジェクトしたコピーはご自身で管理する必要がある — パッケージは以降更新しない |

## レバー1 — グローバル `@theme` トークン

`src/styles/global.css`には、サイトが参照するすべてのデザイントークンを定義する`@theme`ブロックが含まれています。カラー、スペーシング、タイポグラフィ、ボーダー半径、そしてレタースペーシングが含まれます。このブロックでトークンを再定義すると、そのトークンを参照しているすべてのコンポーネントとコンテンツ要素が再テーマ化されます。

```css title="src/styles/global.css"
@theme {
  /* サイト全体のsansスタックを変更 */
  --font-sans: "Inter", system-ui, sans-serif;

  /* 見出しのレタースペーシングを詰める */
  --tracking-tight: -0.04em;

  /* アクセントカラーを変更 */
  --color-accent: oklch(60% 0.22 250);
}
```

レタースペーシングのスケール（`--tracking-tight`、`--tracking-normal`、`--tracking-wide`、`--tracking-wider`）はコンポーネントトークンの整備に伴って追加された、ファーストクラスのグローバルトークンです。ここで`--tracking-tight`を変更すると、`var(--tracking-tight)`を通じて参照しているすべてのコンポーネントに反映されます。

**使う場面:** サイト全体に均一に適用される変更。

**制限:** グローバルトークンはコンポーネントごとに差異を設けることができません。`--font-sans`は本文テキストに適用したいが、見出しには別のフォントを使いたい場合は、そのターゲティングにレバー2が必要です。

パレット/セマンティックトークンのモデルについては[カラー](./color.mdx)を、スペーシング・タイポグラフィ・サイズのトークン一覧については[デザインシステム](./design-system.mdx)を参照してください。

## レバー2 — `--zdc-*` コンポーネントトークン

パッケージのコンポーネントはTailwindユーティリティクラスをハードコードしています（例: `<h1 class="text-heading font-bold">`）。上書きの接合点がなければ、変更する手段は`!important`かイジェクションしかなく、どちらもクリーンではありません。`--zdc-*`トークンはその接合点です。パッケージが公開する、サポート対象のリブランドAPIとして厳選されたCSSカスタムプロパティのセットです。

`:root`でいずれかのトークンを一度設定するだけで、すべてのルートで対象コンポーネントに適用されます。`!important`もイジェクションも不要です。

```css title="src/styles/global.css"
:root {
  /* すべてのページタイトルh1にディスプレイフォントを適用 */
  --zdc-doc-title-font: "Futura", "Century Gothic", sans-serif;
  --zdc-doc-title-weight: 700;
  --zdc-doc-title-tracking: var(--tracking-tight);

  /* プロフォントを見出しフォントから切り離す */
  --zdc-doc-prose-font: "Georgia", serif;

  /* すべてのサーフェスを一括で角丸にする */
  --zdc-surface-radius: var(--radius-lg);
}
```

**`--font-sans`を再定義するのではなく`--zdc-*`を使う理由は?** Futuraでディスプレイ見出しを表示しつつ、本文テキストはシステムsansで読みやすくしたいプロジェクトを考えてみてください。`--font-sans`を再定義するのは誤りです。ナビアイテム、サイドバーのテキスト、コードラベル、そしてグローバルsansトークンを参照しているその他のあらゆるUI要素にも影響してしまいます。`--zdc-doc-title-font`はページタイトルの`<h1>`のみを対象とし、`--zdc-doc-prose-font`はコンテンツのプロエリアのみを対象とします。どちらも他の要素には影響しません。

### 利用可能なトークン

| トークン | 制御対象 |
| --- | --- |
| `--zdc-doc-title-font` | ページタイトル `<h1>` のフォントファミリー |
| `--zdc-doc-title-weight` | ページタイトル `<h1>` のフォントウェイト |
| `--zdc-doc-title-tracking` | ページタイトル `<h1>` のレタースペーシング |
| `--zdc-doc-h2-font` | コンテンツ `<h2>` のフォントファミリー |
| `--zdc-doc-h2-weight` | コンテンツ `<h2>` のフォントウェイト |
| `--zdc-doc-h2-tracking` | コンテンツ `<h2>` のレタースペーシング |
| `--zdc-doc-h3-weight` | コンテンツ `<h3>` のフォントウェイト |
| `--zdc-doc-h4-weight` | コンテンツ `<h4>` のフォントウェイト |
| `--zdc-doc-prose-font` | コンテンツプロエリア（`.zd-content`）のフォントファミリー |
| `--zdc-doc-link-decoration` | コンテンツリンクのテキスト装飾 |
| `--zdc-admonition-radius` | アドモニションブロックのボーダー半径 |
| `--zdc-admonition-border-width` | アドモニションの左アクセントボーダー幅 |
| `--zdc-card-radius` | ナビ/ドキュメントカードのボーダー半径 |
| `--zdc-content-max-width` | ドキュメント読書カラムの最大幅 |
| `--zdc-toc-width` | デスクトップTOC右レールの幅 |
| `--zdc-nav-active-indicator-color` | アクティブなサイドバーナビリンクの背景色 |
| `--zdc-nav-active-weight` | アクティブなサイドバーナビリンクのフォントウェイト |
| `--zdc-surface-radius` | メタノブ: `--zdc-card-radius`と今後のサーフェストークンにチェーンします。`:root`の1行ですべての対応サーフェスを角丸にできます |

<Note>

[デザイントークンパネル](./design-token-panel.mdx)では、セマンティックなスペーシング、フォント、サイズ、カラートークンをブラウザ上でリアルタイムに編集できます。`--zdc-*`コンポーネントトークンはそのスコープ外です。これらは`src/styles/global.css`内の`:root`に一度設定するソースレベルのリブランド接合点であり、実行時にドラッグするノブではありません。

</Note>

**使う場面:** グローバルなデフォルト値とは異なる外観をコンポーネントに持たせたい場合（例: 本文とは異なる見出しフォント、ディスプレイテキストのみにタイトなレタースペーシング、角丸カード、幅の狭いTOC）。

**制限:** 上記のトークンのみがサポートされています。パッケージがトークン化していないプロパティを変更する必要がある場合は、レバー4（スロット）またはレバー5（イジェクション）が次のステップです。

全レジストリと各トークンの背景については[コンポーネントトークン](./component-tokens.mdx)を参照してください。

## レバー3 — 設定（Settings）

`src/config/settings.ts`は、サイトの機能セットと動作を制御します。これらは視覚的なスタイルのノブではなく、構造的な設定です。どの機能が有効か、TOCの深さ、ヘッダーに表示されるアイテム、フッターリンクのリンク先などが該当します。

主な設定項目:

```ts title="src/config/settings.ts"
export const settings = {
  colorScheme: "Default Light",        // Default Light または Default Dark を選択
  colorMode: { defaultMode: "light" }, // デフォルトのライト/ダークモードを変更

  designTokenPanel: true,              // ライブデザイントークンパネルを有効化
  sidebarResizer: true,                // ドラッグ可能なサイドバー幅ハンドル
  sidebarToggle: true,                 // モバイルサイドバートグル
  imageEnlarge: true,                  // 画像クリックで拡大
  dynamicPageTransition: true,         // View Transitions API
  cjkFriendly: true,                   // CJK対応の改行
  mermaid: true,                       // Mermaidダイアグラムのサポート
  aiAssistant: true,                   // AIチャットアシスタントモーダル

  tocMinDepth: 2,                      // TOCに含める最小見出し深さ
  tocMaxDepth: 4,                      // TOCに含める最大見出し深さ
  headingIdStrategy: "hierarchical",   // アンカー生成戦略

  headerNav: [ /* ... */ ],            // トップナビゲーションアイテム
  headerRightItems: [ /* ... */ ],     // ヘッダー右側のコントロール
  footer: { /* ... */ },               // フッターリンクとコピーライト
};
```

**使う場面:** 機能をオンまたはオフにしたい場合、あるいは動作の設定（TOCの深さ、ナビゲーション構造、ロケール設定、2つのバンドルスキームのどちらをアクティブにするか）を調整したい場合。

**制限:** 設定は何が「存在するか」を制御しますが、既存コンポーネントの見た目は変えられません。`colorScheme`は2つのバンドルスキーム（`Default Light` / `Default Dark`）を切り替えるだけで、カタログの切り替えスイッチではなく、変えてもヘッダーのレイアウトを再設計することはできません。実際のカラーストーリーはもう一段深いレイヤーにあります。共有 OKLCH ランプとセマンティックマップを `src/config/color-schemes.ts` で編集し（[Color](./color.mdx#カスタムカラースキームの追加) の「カスタムカラースキームの追加」を参照）、Design Token Panel の Palette タブでランプ編集をライブプレビューし（[カラースキームプレビュー](../guides/color-scheme-preview.mdx#動作の仕組み)を参照）、パネルの JSON 差分ワークフローで AI アシスタントとともに調整をラウンドトリップできます（[Design Token Panel](./design-token-panel.mdx#aiワークフロー)を参照）。

<Info>

レシピスタイルのプリセット（例: 「シャープコーナー」や「セリフ見出し」を一行で適用するもの）は将来的な方向性として検討されています。現時点では、上記のレバー（グローバルトークンと`--zdc-*`）がビルディングブロックであり、プリセットが自動的に適用するものはありません。

</Info>

## レバー4 — `doclayout` スロット

生成された`pages/[...slug].tsx`（ドキュメントレイアウトファイル）には、16箇所のスロットアンカーコメントが含まれています。各コメントは、パッケージファイルを変更することなくマークアップ、スクリプト、またはコンポーネント呼び出しを追加できる、サポートされている挿入ポイントです。

```tsx title="pages/[...slug].tsx（抜粋）"
{/* @slot:doc-layout:after-breadcrumb */}
<AnnouncementBanner />  {/* ← あなたの追加 */}

{/* @slot:doc-layout:body-end-scripts */}
<script src="/analytics.js" defer />  {/* ← あなたの追加 */}
```

利用可能な16のアンカー:

| アンカー | 種別 | 位置 |
| --- | --- | --- |
| `imports` | frontmatter | ファイル先頭のインポート文 |
| `frontmatter` | frontmatter | スクリプトセクション内の変数と式 |
| `head-scripts` | body | `<head>`内、閉じタグの直前 |
| `head-links` | body | `<head>`内のlink/preloadタグ |
| `header-call:start` | body | ヘッダーコンポーネント呼び出しの直前 |
| `header-call:end` | body | ヘッダーコンポーネント呼び出しの直後 |
| `after-sidebar` | body | サイドバーの後、コンテンツカラムの前 |
| `content-wrapper:start` | body | コンテンツラッパーの開始部分 |
| `content-wrapper:end` | body | コンテンツラッパーの終了部分 |
| `breadcrumb:start` | body | パンくずリストの前 |
| `breadcrumb:end` | body | パンくずリストの後 |
| `after-breadcrumb` | body | パンくずリストとドキュメントコンテンツの間 |
| `after-content` | body | ドキュメントコンテンツエリアの下 |
| `footer` | body | フッターエリア |
| `body-end-components` | body | `</body>`閉じタグの前（アイランドマウント用） |
| `body-end-scripts` | body | `</body>`末尾のスクリプトタグ |

**使う場面:** レイアウトの特定位置にクロムを追加したい場合（バナー、アナリティクス用スニペット、追加ナビ要素、クッキー通知など）。

**制限:** スロットはコンテンツを追加します。既存コンポーネントの再スタイリングはできません。既存コンポーネントを再スタイリングするには、グローバルトークン（レバー1）、コンポーネントトークン（レバー2）、またはコンポーネントのイジェクション（レバー5）を使用してください。

## レバー5 — コンポーネントイジェクション

コンポーネントをイジェクトすると、そのソースがパッケージからプロジェクトにコピーされ、ファイルを直接所有できます。イジェクト後は、ローカルのコピーがサイトによってレンダリングされます。そのコンポーネントについては、パッケージのバージョンは無視されます。

```sh
# イジェクト可能なコンポーネントを一覧表示
zudo-doc eject --list

# 特定のコンポーネントをイジェクト
zudo-doc eject header
# → src/components/zudo-doc/header/ にソースがコピーされます
```

イジェクト可能な18コンポーネント:

`header`、`footer`、`breadcrumb`、`toc`、`sidebar`、`theme-toggle`、`page-loading`、`tab-item`、`doc-pager`、`content-admonition`、`code-group`、`details`、`sidebar-tree-island`、`sidebar-toggle-island`、`desktop-sidebar-toggle-island`、`image-enlarge`、`doc-history`、`site-tree-nav-island`

イジェクト後はローカルのコピーを編集します。変更は`pnpm dev`でHMR経由ですぐに反映されます。マークアップの再スタイリング、再構造化、または置き換えを自由に行えます。

**使う場面:** トークンやスロットで必要な変更に届かず、特定コンポーネントの完全なコントロールが必要な場合。

**制限:** イジェクトしたコピーは、パッケージが新しいバージョンをリリースしても更新されません。そのコンポーネントのメンテナンス責任はご自身で負うことになります。将来のAPI変更、バグ修正、パッケージの新機能は自動的には反映されません。

## エスケープハッチ — なぜ `!important` だけでは不十分なのか

zudo-docのパッケージコンポーネントはJSXからTailwindユーティリティクラスを出力します。これらのユーティリティクラスはレイヤーなしのスタイルシートに生成されます — `@layer`ラッパーがないため、カスケードにおいて詳細度が高くなります。独自のスタイルシートで追加したプレーンなCSSルールは、レイヤーなしのユーティリティよりも低い詳細度になるため、無効になってしまいます。

これが`--zdc-*`トークンが存在する正確な理由です。パッケージが出力するバッキングルールはレイヤーなしであり、自身のユーティリティに勝つためのセレクター詳細度を持っています。あなたはトークンの値を再定義し、パッケージのルールがその値を適用します。詳細度の競争も、`!important`も不要です。

`--zdc-*`トークンがないプロパティを上書きする必要がある場合、現時点でのクリーンな選択肢は:

1. ルールに`!important`を追加する（脆弱であり、さらなる上書きを妨げます）。
2. コンポーネントをイジェクトする（レバー5）ことでソースを直接制御する。

カスケードレイヤーの再レイヤリング（パッケージのユーティリティを`@layer`に入れることで、レイヤーなしのコンシューマールールがそれに勝てるようにする）は将来的な方向性として検討されていますが、現時点では利用できません。
