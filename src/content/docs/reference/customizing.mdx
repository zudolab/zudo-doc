zudo-doc ships as a closed package: components live in `node_modules`, stylesheets are compiled, and the rendering pipeline is fixed. Yet projects built on it have widely different branding needs — from a minor color tweak to a fully custom header. This page maps every customization lever available, ranked from the lightest to the most invasive, so you can reach for the right tool without over- or under-engineering the change.

## Decision table

| Lever | Scope | Use when | Limit |
| --- | --- | --- | --- |
| **1. Global `@theme` tokens** | Site-wide | The change applies everywhere (all colors, all text, all spacing) | Cannot diverge one component from the rest |
| **2. `--zdc-*` component tokens** | One component at a time | You want heading/prose typography or layout dimensions that differ from the global defaults, without touching every element that inherits the global token | Only the curated token set is supported |
| **3. Settings** | Feature on/off and configuration | Enabling or disabling features; tweaking TOC depth, sidebar behavior, navigation structure | Cannot change visual rendering beyond what the settings expose |
| **4. `doclayout` slots** | Markup/script injection | Adding chrome (banners, analytics, extra nav items, custom scripts) to specific layout positions | Adds to the layout; does not restyle existing components |
| **5. Component ejection** | Full source control | Total visual control over a specific component | You own the ejected copy — the package no longer updates it |

---

## Lever 1 — Global `@theme` tokens

`src/styles/global.css` contains an `@theme` block that defines every design token the site reads: colors, spacing, typography, border radius, and letter spacing. Redefining a token in this block re-themes every component and content element that reads it.

```css title="src/styles/global.css"
@theme {
  /* swap the sans stack site-wide */
  --font-sans: "Inter", system-ui, sans-serif;

  /* tighten letter spacing for headings */
  --tracking-tight: -0.04em;

  /* shift the accent color */
  --color-accent: oklch(60% 0.22 250);
}
```

The letter-spacing scale (`--tracking-tight`, `--tracking-normal`, `--tracking-wide`, `--tracking-wider`) was added as part of the component-token work and is now a first-class global token — tighten `--tracking-tight` here and every component that chains through `var(--tracking-tight)` picks it up.

**Use when:** the change is consistent across the entire site.

**Limit:** a global token cannot diverge by component. If you want `--font-sans` to apply to body text but a different font for headings, that targeting requires Lever 2.

See [Color](./color.mdx) for the palette/semantic token model and [Design System](./design-system.mdx) for the full spacing, typography, and size token tables.

## Lever 2 — `--zdc-*` component tokens

The package components hardcode Tailwind utility classes (e.g. `<h1 class="text-heading font-bold">`). Without an override seam, the only way to change them would be `!important` or ejection — neither is clean. The `--zdc-*` tokens are that seam: a curated set of CSS custom properties the package exposes as a supported rebrand API.

Set any token once in `:root` and it applies to the matching component across every route — no `!important`, no ejection required.

```css title="src/styles/global.css"
:root {
  /* display font on all page-title h1s */
  --zdc-doc-title-font: "Futura", "Century Gothic", sans-serif;
  --zdc-doc-title-weight: 700;
  --zdc-doc-title-tracking: var(--tracking-tight);

  /* separate prose font from heading font */
  --zdc-doc-prose-font: "Georgia", serif;

  /* round all surfaces at once */
  --zdc-surface-radius: var(--radius-lg);
}
```

**Why `--zdc-*` instead of redefining `--font-sans`?** Consider a project that wants display headings in Futura but readable body text in a system sans. Redefining `--font-sans` is wrong: it also changes nav items, sidebar text, code labels, and every other UI element that reads the global sans token. `--zdc-doc-title-font` targets only the page-title `<h1>`, and `--zdc-doc-prose-font` targets only the content prose area — both without touching anything else.

### Available tokens

| Token | Controls |
| --- | --- |
| `--zdc-doc-title-font` | Page-title `<h1>` font family |
| `--zdc-doc-title-weight` | Page-title `<h1>` font weight |
| `--zdc-doc-title-tracking` | Page-title `<h1>` letter spacing |
| `--zdc-doc-h2-font` | Content `<h2>` font family |
| `--zdc-doc-h2-weight` | Content `<h2>` font weight |
| `--zdc-doc-h2-tracking` | Content `<h2>` letter spacing |
| `--zdc-doc-h3-weight` | Content `<h3>` font weight |
| `--zdc-doc-h4-weight` | Content `<h4>` font weight |
| `--zdc-doc-prose-font` | Content prose area (`.zd-content`) font family |
| `--zdc-doc-link-decoration` | Content link text-decoration |
| `--zdc-admonition-radius` | Admonition block border radius |
| `--zdc-admonition-border-width` | Admonition left accent border width |
| `--zdc-card-radius` | Nav/doc card border radius |
| `--zdc-content-max-width` | Doc reading column max-width |
| `--zdc-toc-width` | Desktop TOC right-rail width |
| `--zdc-nav-active-indicator-color` | Active sidebar nav link background color |
| `--zdc-nav-active-weight` | Active sidebar nav link font weight |
| `--zdc-surface-radius` | Meta-knob: chains into `--zdc-card-radius` and future surface tokens; one `:root` line rounds all opted-in surfaces |

<Note>

The [Design Token Panel](./design-token-panel.mdx) edits the semantic spacing, font, size, and color tokens live in the browser. The `--zdc-*` component tokens are outside its scope — they are source-level rebrand seams you set once in `src/styles/global.css`, not knobs you drag at runtime.

</Note>

**Use when:** you want a component to differ from the global defaults (e.g. a different font for headings vs. body, tight letter spacing on display text only, rounded cards, a narrower TOC).

**Limit:** only the tokens listed above are supported. If you need to change a property the package has not tokenized, Lever 4 (slots) or Lever 5 (ejection) is the next step.

See [Component Tokens](./component-tokens.mdx) for the full registry and the motivation behind each token.

## Lever 3 — Settings

`src/config/settings.ts` controls the feature set and behavior of the site. These are not visual style knobs but structural configuration: what features are enabled, how deep the TOC goes, what items appear in the header, where the footer links point.

Notable knobs:

```ts title="src/config/settings.ts"
export const settings = {
  colorScheme: "Default Light",        // pick Default Light or Default Dark
  colorMode: { defaultMode: "light" }, // override the default light/dark mode

  designTokenPanel: true,              // enable the live Design Token Panel
  sidebarResizer: true,                // draggable sidebar width handle
  sidebarToggle: true,                 // mobile sidebar toggle
  imageEnlarge: true,                  // click-to-enlarge for images
  dynamicPageTransition: true,         // View Transitions API
  cjkFriendly: true,                   // CJK-aware line breaking
  mermaid: true,                       // Mermaid diagram support
  aiAssistant: true,                   // AI chat assistant modal

  tocMinDepth: 2,                      // min heading depth in the TOC
  tocMaxDepth: 4,                      // max heading depth in the TOC
  headingIdStrategy: "hierarchical",   // anchor strategy

  headerNav: [ /* ... */ ],            // top navigation items
  headerRightItems: [ /* ... */ ],     // header right-side controls
  footer: { /* ... */ },               // footer links and copyright
};
```

**Use when:** you want to toggle a feature on or off, or configure behavior (TOC depth, navigation structure, locale setup, which of the two bundled schemes is active).

**Limit:** settings control what exists, not how existing components look. `colorScheme` picks between the two bundled schemes (`Default Light` / `Default Dark`) — it is not a catalog switch, and swapping it does not let you redesign the header layout. The actual color story lives one level deeper: edit the shared OKLCH ramps and the semantic map in `src/config/color-schemes.ts` (see [Color](./color.mdx#adding-a-custom-color-scheme) — "Adding a Custom Color Scheme"), preview ramp edits live via the Design Token Panel's Palette tab (see [Color Scheme Preview](../guides/color-scheme-preview.mdx#how-it-works)), and round-trip tweaks with an AI assistant using the panel's JSON diff workflow (see [Design Token Panel](./design-token-panel.mdx#ai-workflow)).

<Info>

Recipe-style presets (e.g. a "sharp corners" or "serif headings" one-liner) are a possible future direction. Today, the individual levers above (global tokens and `--zdc-*`) are the building blocks — no preset applies them automatically.

</Info>

## Lever 4 — `doclayout` slots

The generated `pages/[...slug].tsx` (the doc-layout file) contains 16 slot anchor comments. Each comment is a supported injection point where you can add markup, scripts, or component calls without modifying any package file.

```tsx title="pages/[...slug].tsx (excerpt)"
{/* @slot:doc-layout:after-breadcrumb */}
<AnnouncementBanner />  {/* ← your addition */}

{/* @slot:doc-layout:body-end-scripts */}
<script src="/analytics.js" defer />  {/* ← your addition */}
```

The 16 available anchors:

| Anchor | Kind | Position |
| --- | --- | --- |
| `imports` | frontmatter | Import statements at the top of the file |
| `frontmatter` | frontmatter | Variables and expressions in the script section |
| `head-scripts` | body | Inside `<head>`, before closing |
| `head-links` | body | Link/preload tags in `<head>` |
| `header-call:start` | body | Immediately before the header component call |
| `header-call:end` | body | Immediately after the header component call |
| `after-sidebar` | body | After the sidebar, before the content column |
| `content-wrapper:start` | body | Opening of the content wrapper |
| `content-wrapper:end` | body | Closing of the content wrapper |
| `breadcrumb:start` | body | Before the breadcrumb |
| `breadcrumb:end` | body | After the breadcrumb |
| `after-breadcrumb` | body | Between the breadcrumb and the doc content |
| `after-content` | body | Below the doc content area |
| `footer` | body | Footer area |
| `body-end-components` | body | Before the closing `</body>`, for island mounts |
| `body-end-scripts` | body | Script tags at the very end of `</body>` |

**Use when:** you want to add chrome (a banner, an analytics snippet, an extra nav element, a cookie notice) to a specific position in the layout.

**Limit:** slots add content; they do not restyle the components that already exist. To restyle an existing component, use a global token (Lever 1), a component token (Lever 2), or eject the component (Lever 5).

## Lever 5 — Component ejection

Ejecting a component copies its source from the package into your project so you own the file directly. After ejection, your local copy is what the site renders — the package version is ignored for that component.

```sh
# list ejectable components
zudo-doc eject --list

# eject a specific component
zudo-doc eject header
# → copies source to src/components/zudo-doc/header/
```

The 18 ejectable components:

`header`, `footer`, `breadcrumb`, `toc`, `sidebar`, `theme-toggle`, `page-loading`, `tab-item`, `doc-pager`, `content-admonition`, `code-group`, `details`, `sidebar-tree-island`, `sidebar-toggle-island`, `desktop-sidebar-toggle-island`, `image-enlarge`, `doc-history`, `site-tree-nav-island`

After ejection, edit the local copy. Changes take effect immediately in `pnpm dev` (via HMR). You can restyle, restructure, or replace markup freely.

**Use when:** no token or slot can reach the change you need, and total control over a component is required.

**Limit:** the ejected copy is no longer updated when the package releases a new version. You take on the maintenance responsibility for that component — future API changes, bug fixes, and new features in the package are not automatically reflected.

## Escape hatch: why `!important` alone does not work

zudo-doc's package components emit Tailwind utility classes from JSX. Those utility classes are generated into an unlayered stylesheet — they have no `@layer` wrapper, which gives them high specificity in the cascade. A plain CSS rule you add in your own stylesheet sits at lower specificity than an unlayered utility, so it loses.

This is the exact reason `--zdc-*` tokens exist: the backing rule emitted by the package is unlayered and has the selector specificity to beat its own utility. You redefine the token value; the package rule applies the value. No specificity fight, no `!important`.

If you need to override a property that has no `--zdc-*` token, the only clean options today are:

1. Adding `!important` to your rule (fragile, inhibits further overriding).
2. Ejecting the component (Lever 5) so you control the source directly.

Cascade-layer relayering (moving package utilities into a `@layer` so plain unlayered consumer rules beat them) is a possible future direction, but it is not available today.
